# R3 性能排查第一轮

日期：2026-09-20。仅修改卡二 R3；稳定单屏及原基线标签保持不变。
目标：全流程可交互阶段持续超过 25 FPS，优先争取 30 FPS。
本轮状态：常态战斗已接近 30 FPS，换房停顿尚未解决，不能标记全流程通过。

## 已实施

- 原启动器每次写入 `info.displayconfig` 的帧率为 24。
  R3 通过独立 `launch_profile.py` 改为默认 30，可选 24/30/60 做对照。
  稳定 `packaging/launch.sh` 不变；未用 60 FPS 做设备验收。
- 加入可关闭的 Java 帧/更新耗时计数，以及有大小上限的 GC/safepoint 日志。
  Java render 耗时包含 update，并非纯 GPU 耗时；没有添加逐帧 GPU 同步。
- 高频 XML 状态、触摸心跳、采集状态和帧 CSV 写到会话专属 `/tmp` 目录；
  正常退出和独立恢复后归档到卡二，路径/文件白名单检查后清理。
  GC、启动器日志仍在卡二；不宣称消除了全部写卡。
- R3 初始 Java 堆从 128 MiB 调为 64 MiB，上限仍为 140 MiB，
  保留 SerialGC；提供初始堆及 GC 对照参数，但其他 GC 尚未实机测试。
- 没有降低分辨率、移除背景、降低纹理质量、修改固件/频率或配置 swap。
- 修复截图状态 JSON 未显式指定 UTF-8 的问题。

## 卡点判断

1. **已确认的帧率上限**：24 FPS 来自配置，而不是已测硬件性能上限。
   调到 30 后原有双屏渲染仍能维持常态约 30。
2. **GC 不是全部原因**：最终战斗窗口 GC 多为 5～12 ms；
   三个 >100 ms 帧均未与已记录 GC pause 重叠。
   1041.59 ms 帧位于地图进入新战斗附近，需继续拆分资源加载、
   首次类加载/编译、纹理上传和文件访问；尚未确认根因。
3. **内存余量仍小**：最终资源日志 VmRSS 约 524 MiB，可用内存约 78 MiB。
   同时读取的 smaps_rollup RSS 约 413 MiB，与 status 的 RSS 计数不一致，
   两种原始值都保留，不能当作已证实的 100 MiB 内存节省。
   Java 活跃堆约 13～30 MiB，降低 Xms 并不等于总进程内存同比减少。
4. **截图不是已确认的长期退化原因**：同一次 RAM 诊断运行截图前后
   smaps RSS 仅小幅变化，没有证实截图导致持续增长。
5. **功能范围**：本轮组合验证主菜单、继续游戏、战斗、选敌出牌、
   敌人回合、奖励、选卡、地图、事件和下一战斗。商店、休息、
   精英/Boss、第二/三幕、大量状态/特效尚未覆盖。
   非战斗房间仍是既有下屏整页回退，上屏黑屏属于未完成的布局范围。
