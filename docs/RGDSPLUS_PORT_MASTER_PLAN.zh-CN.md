## 1. 总原则与终点

**先完成可以独立交付的单屏版本，再开始双屏画面的拆分。**

```text
S0 固定基线与恢复能力
 -> S1 完整输入与文本输入
 -> S2 单屏游戏逻辑 + S3 单屏显示
 -> S4 性能与音频
 -> S5 存档、生命周期与长稳
 -> G-S 单屏总验收、冻结回退版本
 -> D0 双屏显示/触控探针
 -> D1 两套布局原型与对比
 -> G-D 选择正式布局
 -> D2 全场景双屏适配
 -> D3 双屏稳定性与发布验收
```

- 按第 0 节的最新授权启动双屏预研；真实游戏实验保持隔离、可退出与可回退，
  不为布局改变规则逻辑，不替换稳定单屏入口。
- 单屏的“完成”包括离线完整游戏闭环、所有必需输入、正常显示、稳定帧时间及可靠存读档。
- 双屏始终只有一个游戏实例、一套规则状态、一套随机数状态、一份权威存档。
- 公开交付始终是无游戏资源适配包，用户手动放入正版 `desktop-1.0.jar`。
- 当前重点转为双屏全界面分配与跨屏瞄准设计；保留已验证的原生 4:3、
  纹理与输入修复。单屏证据缺项继续留档，不改变系统固件。

### 1.1 第一版范围

纳入：原版离线内容、四个角色、解锁/进阶、普通与自定义/种子局、可到达的完整章节、
设置、图鉴、统计、存档管理、手柄操作，以及后续双屏所需的触控。

默认语言验收范围为简体中文和英文；其他语言未测不得宣称支持。
ModTheSpire/BaseMod、玩法 Mod、Steam 在线服务、云存档同步、排行榜、
联网每日挑战和其他固件/掌机不作为第一版承诺。
不可用的在线入口必须可返回、无卡死，并在支持范围中明确说明。
若要把上述内容纳入正式支持，单独增加验收项，不能暗中扩大“全功能”定义。

## 3. 借鉴小丑牌，但不照搬旧方案

以小丑牌较新的移植手册、当前源码和证据索引为依据。

| 借鉴点 | 杀戮尖塔中的落实 |
| --- | --- |
| 同一实例拆显示 | 不开第二个 Java 游戏实例，不用独立地图实例 |
| 输入只有一个有效来源 | 明确 SDL、gptokeyb、虚拟手柄、触摸各层的职责与去重 |
| 对象生命周期比截图重要 | 拖拽、弹窗、教程、奖励、商店对象离场时一起清理输入和显示 |
| 软件/模拟/物理证据分开 | 测试脚本通过不代替实体按键和手指验收 |
| 隔离测试存档 | 测试前检查目录、档案、副作用、备份和恢复方式 |
| 每轮有完整证据 | 构建标识、操作记录、日志、帧时间、画面和结论绑定 |
| 公私包分离 | 私有游戏、派生 JAR、存档和截图不进入公开适配包 |

小丑牌的 Lua 回调及对象重排不能直接用于 Java/LibGDX，必须重新审计接入点。

## 4. 架构与数据边界

### 4.1 保留的单屏基础

- 以用户 PC 版 1024×768 截图为布局参考，采用原游戏 `isFourByThree` 分支，
  不将 16:9 整帧拉伸或裁切伪装成 4:3。逻辑尺寸、窗口、drawable 均需为 1024×768。
- 分开验收布局、纹理/透明度、渲染顺序与屏幕呈现。缓冲区截图中的条纹不直接
  归为垂直同步问题；没有实机动态证据，不宣称屏幕撕裂已消失。
- 系统 Weston 和音频服务继续运行；不直接抢占 DRM，不永久改 DT/udev。
- `launch.sh` 管理会话、运行时和退出；`run-java.sh` 记录真实 Java PID/退出码。
- 显示修正和输入代理保持可单独关闭/回退，修改基于证据，不把所有异常都归于一个原因。
- 游戏原件只读；派生缓存按原件哈希与适配版本区分，损坏缓存不得作为成功构建。

### 4.2 输入、规则与显示分开

```text
实体设备 -> 设备映射 -> 输入事件/状态 -> 原游戏动作 -> 唯一游戏状态
                                               -> 单屏或双屏显示
```

现有 gptokeyb + 虚拟手柄先完成单屏，不预先重写整个输入引擎。
若它不能可靠处理文本、短按或混合输入，再有针对性替换接口，并跑同一套回归。
多路输入不能各自对同一个游戏动作提交一次。

### 4.3 存储和回滚

- 卡二为当前权威目录；卡一转发不创建第二份档案。
- 实测确认全部写入位置，至少覆盖 `saves/`、`betaPreferences/`、显示与控制设置。
  不能假定 `XDG_DATA_HOME` 已接管一切。
- 适配版本、缓存和玩家数据分离；更新不覆盖玩家数据。
- 留存上一套可启动的适配材料和构建清单；回滚前检查游戏存档版本兼容性。
- FAT32 下按真实文件系统验证安装提交/失败恢复，不依赖符号链接或未经测试的持久性假设。
- 测试进程只写隔离目录；发布包不带自动点击、改存档或远程控制测试入口。

## 5. 单屏阶段与逐阶段验收

### S0：可复现基线与退出保障

工作：冻结固件、原件哈希、上游版本、代理、运行库、启动参数；补全诊断与恢复。

通过标准：

1. 从掌机菜单连续启动/正常退出 10 次，冷启动 3 次；没有重复 Java、输入助手或遗留窗口。
2. Back/Select 与独立返回键各测试短按、持续按住和重复按下；短按不得触发强退。
3. 持续约 1.5 秒触发退出，容差目标 ±0.2 秒；从触发起 4 秒内结束可终止的卡死进程，
   10 秒内回到可操作菜单。正常路径与 SIGSTOP 路径各重复 5 次。
4. 单实例锁、菜单恢复、原有菜单已暂停、异常信号、运行时挂载清理各有测试。
5. 日志同时记录 Java/渲染线程异常和真实退出状态，不以退出码 0 单独判成功。
6. 热缓存启动 10 次，目标 P95 ≤60 秒且单次 ≤90 秒；首次构建另测，必须显示阶段/进展。
   缺依赖、错误 JAR、缓存损坏、缺卡和空间不足有明确可返回的错误。

产物：环境清单、启动/退出测试报告、故障恢复说明、可复现构建标识。

### S1：完整输入与无需键盘的使用闭环

工作：逐界面建立动作表，修复输入处理器切换、焦点、按住状态及文字输入。

通过标准：

1. 所有面键、方向、摇杆、肩键、扳机、Start/Select 按真实机身标签校准；
   提示图标与实键一致，记录确认/取消在不同页面的实际语义。
2. 每个映射做 30 次短按和 10 次按住/松开；无串键、重复动作、丢松开或残留选择。
3. 命名、重命名、设置、卡牌详情、地图、奖励、商店、暂停等界面切换至少 50 次，
   返回后仍可操作，不出现输入处理器替换后失效。
4. 正式补齐手柄可操作的屏幕键盘/字符选择器：自定义名字、种子、删除字符、清空、
   确认和取消；中文系统界面必须可读。第一版文字输入至少支持拉丁字母、数字、
   空格及相应字段允许的符号；中文姓名输入作为明确的后续范围，不默认声称已有。
5. 默认 `RGDS 1/2/3` 保留为快捷路径，但不能作为“文本输入全部完成”的证据。
6. 手柄可独立完成所有支持范围内的必需操作，不需要 SSH 或实体键盘解卡；
   外接键盘作为选配输入时也不能被代理错误吞掉。
7. 初始单屏可先在上屏做手柄验收；触控验收时把同一个完整单屏画面放到下屏，
   不拆画面、不启用双屏布局。下屏定位不可用应先修单屏输出选择。
8. 下屏单屏触控完成点击、拖拽、目标选择、取消、滑动/详情，并与手柄混用通过；
   若暂不完成该项，仍可标记“单屏手柄测试版”，不得通过本计划的 G-S。

产物：页面动作表、文本输入交互、按键与触控回归记录。

### S2：单屏游戏逻辑完整性

工作：优先沿用原规则，查清上游补丁及代理触及哪些规则/输入接入点。

| 流程组 | 必须覆盖 |
| --- | --- |
| 战斗 | 单体/群体目标、攻击/技能/能力、零费/X 费、能量不足、不可打出、目标死亡与取消 |
| 牌堆 | 抽牌、弃牌、消耗、洗牌、检索、生成牌、满手牌、选择多张及确认 |
| 状态 | 力量/敏捷、毒/虚弱/易伤、格挡、持续效果、回合开始/结束、敌人多段行动 |
| 角色特性 | 四角色代表性机制，含球与充能/激发、姿态切换及对应多目标场景 |
| 消耗与反馈 | 药水使用/丢弃/满槽、遗物触发、敌人意图、伤害数字与死亡 |
| 跑图 | 地图合法路径、普通/精英/首领、事件、营火、宝箱、奖励、商店和移除/升级选牌 |
| 结局 | 失败、重开、胜利、继续、解锁及额外章节入口/结束 |
| 周边 | 图鉴、统计、设置、自定义/种子局、进阶选择、退出与返回 |

通过标准：

- 四角色各完成至少一轮三幕流程；另覆盖一次可用的额外章节完整流程，
  至少两次失败/重开，以及一组高复杂度后期存档。
- 核心动作序列按状态变化检查：费用、血量、格挡、牌堆、目标及奖励没有多执行/漏执行。
- 使用同版本基线、隔离存档和已知操作序列作对照。相同种子不自动等于相同执行路径；
  如上游游戏版本不同，先确认差异，不能把差异直接算成移植错误。
- 自动化辅助可以加速覆盖，但至少一条完整流程由用户实体操作；测试不能修改生产档案。
- 覆盖代表性机制与边界组合，保留未覆盖风险；不宣称有限测试等于验证每张牌的全部组合。

产物：流程覆盖表、代表性测试存档索引、关键状态对照、缺陷清单。

### S3：单屏画面、文字与反馈

工作：逐场景对照画面，检查 ASTC/纹理处理、字体、坐标、动画和特效。

通过标准：

1. 覆盖 S2 全部页面，收集静态图和动作视频；无黑屏、系统画面遮挡、错层、残影、
   缺图、错误透明、异常颜色、持续闪烁或可见的严重撕裂。
2. 画面比例正确，逻辑坐标、视觉位置和 hitbox 一致；放大详情后仍可返回与操作。
3. 中文/英文的卡牌标题、描述、数值、长遗物栏、满手牌、弹窗和多选列表无截断或遮挡。
   关键正文建议不低于约 18 像素字高；密集卡牌必须有易用的放大查看途径，
   最终以设备上的可读性验收，不靠无限缩字通过。
4. 所有战斗关键反馈都可辨认：选中卡牌、当前目标、费用不足、有效/无效落点、敌人意图。
5. 无 SSH 的冷启动、返回系统后重进、关屏/恢复后画面都能正确呈现。
6. 原生截图不可用时用设备拍摄，不能仅凭“进程活着/渲染函数被调用”判画面正常。

产物：场景画面索引、坐标/文字问题表、实体显示确认记录。

### S4：稳定帧时间、内存与音频

工作：建立可重复性能场景，区分加载、稳态、转场和压力场景，再逐个优化。

**以下数值是拟定验收门槛，不是当前实测完成值。**
基于现有配置先锁定 F=24 FPS 的单屏基线；30 FPS 作为优化目标，不预先承诺。
若性能阶段证明能稳定 30，则正式改为 F=30 并重跑全部性能矩阵。
不能通过降低门槛、缩糊文字或少画必要信息来把失败标成通过。

| 指标 | 单屏拟定通过标准 |
| --- | --- |
| 场景样本 | 菜单、普通战斗、多敌人/特效压力战斗、满手牌详情、地图、商店各测 5 分钟 ×3 轮 |
| FPS | 各稳态样本均值 ≥0.98F；任意连续 10 秒窗口均值 ≥0.90F |
| 帧时间 | P95 ≤1.5×1000/F，P99 ≤2×1000/F；F=24 时约 62.5/83.3 ms |
| 停顿 | 稳态 >100 ms 的帧占比 ≤0.1%，不得出现连续跳过游戏逻辑；无未解释的 >250 ms 停顿 |
| 输入反馈 | 物理动作到可见响应 P95 ≤150 ms、P99 ≤250 ms，不把动画执行时长当输入延迟 |
| 内存 | 预热后 Java RSS 目标 ≤650 MiB；稳态 `MemAvailable` ≥100 MiB，无 OOM/分配失败 |
| 增长 | 相同场景循环 2 小时，前后可比的 5 分钟内存中位数差 ≤30 MiB，且没有持续上升趋势 |
| 音频 | BGM/音效 30 分钟压力测试无可闻断续、爆音、错误静音或重复播放；播放设备切换可恢复 |
| 转场 | 暖缓存常规页面切换目标 P95 ≤2 秒；较重加载单列预算、可见反馈，不能伪装成无响应 |

测量要求：

- 采集逐帧分布及游戏更新计数，不能只看 5 秒平均 FPS。
- 分开统计游戏渲染、逻辑更新与实际屏幕呈现；物理视频/用户确认负责显示链证据。
- 预先标注加载区间，不能测完后为了漂亮数字任意删掉卡顿片段。
- 帧时间超限同时查 CPU、GC、RSS、可用内存、纹理/音频 I/O、温度/频率及换帧等待。
- 24 FPS 限速并不自动证明稳定；已有 swap interval 修正还需 S3 的显示质量回归。
- 内存计入原生纹理、OpenAL、兼容层与系统服务；不要把 `-Xmx` 当进程总预算。
- 若某指标不达标，明确阻塞原因和修改方案；修改阈值必须有记录及用户认可。

产物：原始逐帧数据、分位数报告、压力存档、音频与显示观测、优化前后对比。

### S5：存档、生命周期、安装和长稳

通过标准：

1. 3 个档案的创建、选择、重命名、删除、取消均通过；删除需要明确确认，
   取消不改变档案。默认名与自定义名都测。
2. 在地图、战斗入口、奖励后、商店后等原游戏支持的检查点做 10 组保存退出/重启继续。
   验证人物、血量、牌组、遗物、金币、进度；不要求在任意动画帧保存。
3. 应急退出后能读取上一个有效检查点。写入中断/满卡等故障只在隔离测试区注入，
   不在用户活动内存卡上直接断电来“验收”。
4. 单次连续混合游玩 ≥2 小时，累计 ≥8 小时；另做菜单/地图/商店/战斗反复进出 ≥100 次。
   无崩溃、无输入锁死、无持续音频断续、无无界内存增长。
5. 关屏/恢复 10 次、合盖/开盖 10 次、充电状态切换、耳机插拔各做记录；
   不把关屏当成已验证系统 suspend。固件不支持的状态单列，不作虚假承诺。
6. 热状态与电量较低时各重复性能代表样本；记录实际条件，不主动关闭系统安全保护。
7. 清洁安装、已有档案升级、上一适配版回滚各 3 次；原件、档案、配置不被覆盖。
8. 卡二缺失不误启卡一旧副本；空间不足、构建中断和损坏缓存不破坏已有可用版本。
   安装前空间预算按实测工作集峰值加至少 256 MiB 余量核算。
9. 错误报告可追溯；日志限量/轮转有预算，长期开启调试不应撑满卡。

产物：存档一致性与恢复报告、长稳日志、安装/回滚报告。

### G-S：单屏总门禁

正式单屏冻结需同时满足以下条件；研究阶段按第 0 节的新授权和隔离边界执行：

- S0～S5 的全部阻塞项通过；无 P0/P1 缺陷，无未解决的错误出牌/错目标、输入死路、
  数据损坏、必要信息不可读或持续卡顿。
- 实体按键和手指测试都有证据；全流程游戏不依赖电脑、SSH、外接键盘。
- 普通用户从无游戏文件的包开始，按文档放入正版文件后能完成安装到继续游戏。
- 样本、数值和未覆盖范围有书面报告；用户确认单屏体验可以作为独立可用版本。
- 留存单屏候选包、哈希、构建说明和备份/回退路径。
- 次要缺陷若保留必须逐条列明影响，不得把阻塞项降级为“已知问题”绕过门禁。

**未补齐的证据保持未验收；不以双屏新布局掩盖已知显示、输入或性能问题。**

## 6. 双屏公共准备：D0

按最新授权可以开展隔离研究。接入前保留单屏构建及哈希、独立测试档案、
已验证退出路径；第一步仍不是拆战斗。正式交付不因研究授权省略验收。

1. 在实际固件上重新确认上下屏、逻辑输出排列、触摸设备名、轴范围、旋转和焦点。
   小丑牌的左右布局只是参考，不能把某个 event 编号或 DSI 编号写死。
2. 先做编号/边界/触点测试，再试一个进程中的双视口合成；是否采用 2048×768
   单窗口、两张 FBO 以实测决定。一个宽窗口不等于可以把游戏整体横向拉伸。
3. 建立设备坐标、窗口坐标、上下屏局部坐标、游戏坐标、逆向命中五层转换。
4. 帧缓冲、字体与纹理有资源预算：RGBA8 的 1024×768 色彩缓冲约 3 MiB，
   两张约 6 MiB；这不含深度、多缓冲、驱动和缓存，不能把总显存需求说成只有 6 MiB。
5. 单指 owner、第二指忽略/取消、越界、`SYN_DROPPED`、设备消失、失焦、弹窗、
   切场景、输入源切换都能释放拖拽，不能重复提交一次操作。

通过标准：每屏网格/角点命中误差目标 ≤8 个逻辑像素，无上下屏混淆；
200 次点击/拖拽无软件重复/卡住；20 次取消/失焦可恢复；
双屏探针连续 30 分钟无黑屏、闪烁和资源增长，并能一键配置回单屏。

## 7. 方案 A：上屏战斗，下屏手牌与向上拖拽

### 7.1 分工

| 区域 | 内容 |
| --- | --- |
| 上屏 | 原生顶部工具/状态栏、玩家、敌人、意图、生命/格挡、状态、战斗特效与目标反馈；顶栏及药水局部菜单主要通过手柄操作 |
| 下屏 | 原生最底层背景+迁移的装饰前景、完整手牌、能量/费用、结束回合、抽/弃/消耗牌堆、卡牌详情与瞄准区；不复制常驻顶栏 |
| 非战斗 | 地图/信息可在上屏展示，但需要操作的选项必须能在下屏或通过手柄完成 |

不把一张静态战斗截图贴到上屏，不同时维护两份手牌或两套敌人 hitbox。

以下为用户提出的优先设计方向，隔离原型按第 0 节及新预研文档推进：

- 前景按绘制对象/层分配，不从最终画面沿水平线硬切，避免把人物、特效或浮层截断。
- 装饰前景只在下屏出现，上屏不再绘制；地面、阴影、战斗提示不是可随意删除的装饰。
- 下屏各页面都有原生底层背景或明确继承来源；模态页继承父场景，不能重复更新背景状态。
- 顶栏入口留上屏，但地图/牌组/设置完整页面仍按交互分工打开到下屏；
  药水局部菜单和选敌保留原生上屏手柄流程，返回恢复正确焦点。
- 手牌在下屏略靠下，但不贴底；整张卡牌、选中放大与底部边框均应可见。
- 相对原生单屏手牌适度放大，具体比例由满手牌、中文说明、控件安全区实测决定，
  不先写死放大倍数。普通手牌与满手牌都要保证可选择、可看全。
- 能量、结束回合、牌堆使用固定安全区；卡牌扇形展开与详情不得遮住必要操作。
- 绘制变换和逆向 hitbox 变换一起修改；拖拽、选中放大、说明浮层和出牌特效
  分别确定所属屏幕，不把“截图看起来正确”当成交互正确。

### 7.2 “拖往上屏”的真实实现

按目前只有下屏触摸的设备条件，**手指离开下屏后无法继续获得上屏触点**。
不能要求物理跨屏拖动，也不能把“碰到下屏上边缘”直接当作合法出牌。

最新优先方向为下屏拖动方向映射上屏敌人，加有限吸附与高亮；
下屏绝对位置瞄准区保留为对照/精确选择候选，不能在手势中无提示切换算法。
跨屏箭头使用物理上下排列的虚拟画布计算，再分别裁剪到实际输出。
详细坐标、歧义目标、松手校验和输入仲裁见新预研文档第 6～9 节。

```text
下屏点住卡牌 -> 明确向上拖动 -> 按方向选择上屏合法目标
 -> 上屏目标高亮 + 下屏目标反馈 -> 合法目标上松手提交
 -> 拖回/越界/目标无效/按 B/失焦则取消
```

- 主方案用固定起点的拖动方向与上屏目标投影匹配；几何歧义不强行吸附。
  绝对位置映射仅作为明确切换的备选模式，卡牌区仍用下屏局部坐标。
- 单体牌需要明确目标；无目标/群体/自选牌走各自原有合法性检查。
- 指针跨分区时锁定同一张牌和同一操作，不丢失 owner，也不重复扣费。
- 目标死亡、手牌变化、打开弹窗或转场必须取消旧引用，不能使用已销毁对象。
- 永久保留原生按键选牌/选敌；触摸与手柄共享唯一目标状态，详情查看与出牌动作必须可区分。
- 虚线在下屏上沿与上屏下沿视觉接续；铰链间隙不绘制，两段不是独立演进的两根箭头。

### 7.3 优缺点与专门门槛

优势：上屏战斗完整，手指不遮敌人；下屏可以给手牌更多空间。
风险：视线跨屏、远端目标选择、卡牌拖拽与战斗特效的重排都更复杂。

验收：

- 单体/群体/无目标、满手牌、多敌人、小目标、目标消失与取消路径全部通过。
- 200 次受控出牌/取消无软件造成的错牌、错目标、重复扣费或悬空拖拽。
- 用户至少完成两轮每轮 20 次目标选择任务；首次目标命中率目标 ≥95%，
  记录误操作原因和完成时间，不把软件正确率与人的命中率混为一谈。
- 无法看清选中敌人或需要猜测松手位置即不通过。
- 满手牌、选中放大、卡牌详情、抽牌/弃牌/消耗动画中没有底边裁切、跨屏半张牌、
  前景重复绘制或必要控件遮挡；下屏调整大小后指针与卡牌 hitbox 仍一致。
- 不为方案 A 修改卡牌规则、命中资格或随机结果。

## 8. 方案 B：下屏完整战斗，上屏地图与辅助信息

### 8.1 分工

| 场景 | 下屏主要操作 | 上屏辅助展示 |
| --- | --- | --- |
| 战斗 | 完整战斗场景、手牌、目标、结束回合与药水 | 当前地图位置/已知路线、选中卡牌或敌人的放大详情 |
| 地图选路 | 可点击的合法路线或当前可选节点列表 | 全图总览与当前位置 |
| 商店/事件/营火/奖励 | 原场景与所有选择 | 牌组/遗物摘要、相关说明，按场景选择，不同时堆满 |
| 卡牌详情/牌组 | 当前选择、滚动、确认/取消 | 大字卡牌或比较信息 |
| 菜单与设置 | 完整可操作界面 | 档案/状态摘要或非交互背景 |

第一原型只做“下屏原战斗 + 上屏只读地图/位置”，其他辅助信息后加。
上屏不能显示原游戏尚未公开的信息、提前触发事件或运行一次额外地图更新。
地图选路仍必须在合法阶段提交，战斗期间上屏地图只读。

### 8.2 优缺点与专门门槛

优势：卡牌与敌人在同一触屏，拖拽路径直接，较容易保留已验收单屏布局。
风险：手指可能遮挡手牌/目标；上屏地图在战斗中可能价值有限；
地图双视图的选中、滚动和当前节点必须同步。

验收：

- 下屏战斗与 G-S 的输入/逻辑测试全部重跑，不因上屏显示而触发额外规则更新。
- 100 次场景/地图切换后无过期节点、高亮残留、跳路线或双重选择。
- 上屏只读区域不截获下屏输入；所有可操作选择都有下屏或手柄路径。
- 相同任务的操作时间、误操作和遮挡不明显劣于单屏，必须由用户试用确认。

## 9. D1 原型对比与 G-D 布局选择

**按用户最新方向优先设计 A 的“上屏观看、下屏操作”全界面方案；
B 保留为对照和回退候选。隔离研究已获授权，不与正式发布验收混淆。**

若进行两套原型比较，使用同一个留存的单屏基础、相同隔离存档和相同场景；
只比较呈现/交互，不各自改规则和性能预算。

| 对比维度 | 记录方式 |
| --- | --- |
| 操作正确性 | 指定牌/指定目标出牌、取消、药水和结束回合的错误记录 |
| 效率 | 普通一回合、多敌人目标选择、卡牌详情查看的耗时 |
| 可读性 | 敌人意图、中文卡牌、满手牌、地图路线的实体阅读 |
| 触控体验 | 遮挡、误触、拖拽边界、跨屏视线切换和疲劳反馈 |
| 性能成本 | 同一场景帧时间分位数、内存、温度和音频表现 |
| 工程风险 | 改动对象数量、原行为回归、渲染状态与生命周期复杂度 |

决策规则：

1. 先否决存在错误出牌、不可恢复拖拽、信息缺失或性能门槛不达标的方案。
2. 对通过者做用户实际游玩对比，记录偏好及原因，不凭静态效果图定案。
3. 若只有 B 达标，可先交付 B，A 保留实验状态；若都未达标，保留单屏而不是降低门槛。
4. 暂不承诺两种正式模式同时维护；是否双模式由维护成本与用户确认决定。
5. 模式切换先限于启动/主菜单等安全状态。中途拖拽、结算或写档时禁止切换。

## 10. D2 全场景双屏与 D3 发布门槛

### D2：所有界面与生命周期

- 逐项把 S2/S3 的场景映射到上下屏，不只拆战斗演示。
- 统一管理 tooltip、弹窗、教程、卡牌选择、结算、过渡和全屏特效。
- 游戏逻辑和动画状态每个逻辑帧只更新一次；两次 render 不得再次抽牌、扣费或抽随机数。
- 保存并恢复绘图状态，屏幕切换不污染下一块视口；下屏输入用逆变换命中。
- 静态地图按状态变化更新缓存，不在每帧重建全图；优化不能显示旧状态。
- 单屏和双屏共享规则/存档格式，布局设置独立；返回单屏后仍能继续同一有效档案。

验收：S2 流程矩阵与 S3 画面矩阵在正式双屏布局上全部重跑；
额外完成 200 次拖拽、100 次场景切换、20 次失焦/取消和安全模式切换测试。
软件造成的错误提交、重复动作、悬空对象和跨屏命中错误均为零容忍阻塞。

### D3：性能、长稳与发布

- 继承单屏冻结的 F 与帧时间门槛，不能默认为双屏允许降帧。
- 双屏仍满足系统可用内存底线；新增资源逐项计量并复测 2 小时增长。
- 四角色完整流程、额外章节、失败/胜利、存读档与安装/升级/回滚再次通过。
- 单次 ≥2 小时、累计 ≥8 小时双屏游玩，无阻塞缺陷；至少一轮由用户实体操作。
- 单屏稳定包始终保留，双屏出现问题可回退，不改坏玩家原件和档案。

公开包必须再通过：

1. 白名单检查，无正版 JAR、派生游戏 JAR、原版素材、玩家数据、私有日志或凭据。
2. 从干净环境按文档完成安装、放入正版文件、构建、启动、退出、继续。
3. 原件哈希、上游版本、适配构建版本、运行时依赖和第三方说明可追踪。
4. 完整构建命令包括 Java 输入代理和 ARM64 shim，不能只靠开发机残留二进制。
5. 测试入口不随公开包部署；发布文档写明固件/语言/功能范围和未解决限制。
6. 用户确认后才发布；本计划不授权自动上传或公开任何测试资源。

## 11. 证据、缺陷与验收纪律

状态只用：`未测`、`实现中`、`软件通过`、`实机模拟通过`、`物理通过`、`失败`、`门禁通过`。
不能把局部实测直接升级成整阶段通过。

每条记录至少包含：

```text
用例 ID / 构建及原件哈希 / 固件 / 输入来源
前置存档副本 / 操作步骤 / 期望 / 实际 / 重复次数
日志及帧时间文件 / 截图或视频 / 结论 / 缺陷编号 / 复测版本
```
