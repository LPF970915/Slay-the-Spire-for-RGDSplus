# R4 触控、音频与卡顿修复

构建标识：`r4-touch-20260920-8`。这是可交互测试版，不是全流程验收完成版。

后续 U09 交互改为最近目标锁定与横向切换，见
[R4 拖牌锁定修订](R4_DRAG_LOCK.zh-CN.md)。本文保留该历史构建的修复与证据，
不能把旧方向角度算法或旧截图视为新构建的当前行为。

## 问题与修复

1. 旧截图版硬编码关闭音频、触摸仅采集，误用于手动游玩。
   R4 菜单入口现在默认启用音频与真实游戏触控；
   review 仍需显式 `--audio --touch-live`，R3 保留原默认行为。
2. 上游 controller transformer 会重新读取原类，覆盖早注册的输入 hook。
   双屏 agent 改在可重转换阶段接入，并用实际三层 agent 链测试，
   不能只验证对原始 JAR 单独转换成功。
3. 保留已确认的 evdev、tpctrl、焦点独占和恢复模块，使用会话内 loopback
   将有序 DOWN/MOVE/UP/CANCEL 投递到游戏更新线程，不另行注入 SDL 鼠标。
   Hitbox 用实际渲染矩阵反变换；上屏、未绘制、过期控件不接受下屏点击。
4. 首次触摸退出原生手柄选牌模式，避免点牌堆时打出此前高亮的防御。
5. 战斗单独接入拖牌：命中实际下屏手牌、按绘制次序处理重叠，
   跟随手指、固定起点方向选敌、原生目标高亮、原生素材跨屏曲线。
   未命中或方向歧义时保留方向线，但不允许提交。
6. 松手仍调用原版 `canUse` 和 `playCard`，不直接扣能量、伤害或改牌堆。
   目标至少显示一帧后才允许提交；快速释放可冻结目标等待下一帧。
   B、多指、手柄接管、失焦、断连、过期事件、拖回、边缘释放均取消。
7. `AbstractPlayer.updateInput` 还负责推进待结束回合。
   触控接管仅在选牌阶段阻止原单屏解释；回合结束请求/敌人回合必须交回原代码。
8. 启用音频后旧配置发生持续内存回收/磁盘缺页。
   R4 改为 Xms32 / Xmx128、SerialGC、TieredStopAtLevel=1；
   R3 仍为 64/140、tier 4。没有改固件、频率、swap、纹理或单屏目录。

## 实机证据

所有证据在忽略目录 `validation/r4-review/`。截图是 framebuffer，
输入为 evdev 软件注入；不替代实体触点精度、手感、扬声器听感验收。

- `combat-pile-*`：手柄高亮手牌后点击抽牌堆，手牌/弃牌/能量/敌人状态不变。
- `combat-cancel-b-*`、`combat-cancel-second-*`、`combat-drag-back-*`、
  `combat-edge-*`：选牌/瞄准后取消，玩法状态不变。
- `combat-strike-*`、`combat-high-*`：打击拖动与跨屏原生曲线，
  下屏 y=70 仍能瞄准；一次释放对应能量 -1、手牌 -1、弃牌 +1，
  目标按原版规则受伤，不能只看箭头判定出牌成功。
- `combat-defend-*`：无敌人目标的防御向上拖动，原版格挡 +5。
- `combat-end-turn-1789923944975977900.json`：触摸结束回合后，
  敌人实际攻击、玩家生命变化，下一回合恢复 3 能量并抽到 5 张牌。
- 最终适配器 SHA256：
  `e7e0adcb0c1267f2fc7540755a05aa7c1e306a0177b071186e04ccb6a2686dd5`。
  同版连续通过牌堆、B/多指/拖回/边缘取消、攻击、高位攻击、防御和结束回合。
- 触摸后通过原生手柄注入重新选牌、进入选敌、左右切换并 B 取消，
  能量不变；长按 Select 退出后所有会话锁释放、菜单恢复、tpctrl 恢复 0，
  审计为 `audit-1789924379939943642.json`。

  Java stream 已启用且未静音；显式扬声器输出 monitor 采样非零 PCM

### 性能对照

| 配置/窗口 | 平均 FPS | P95/P99 ms | 最大 ms | >100/>250 ms |
| --- | --- | --- | --- | --- |
| Xms32/Xmx128、tier 4，约 90 秒 | 29.39 | 37.28 / 53.79 | 684.00 | 10 / 4 |
| 同堆配置、tier 1，约 87 秒 | 29.97 | 37.84 / 75.93 | 113.08 | 1 / 0 |
| 最终版、tier 1，约 179 秒完整战斗输入回归 | 29.98 | 37.62 / 76.23 | 168.69 | 3 / 0 |

两窗包含战斗触摸注入；仅排除截图及相邻帧，不丢弃其他慢帧。
不是严格同一帧回放，不能把差异全部归因于单一参数。
tier 4 的 90 秒系统缺页增量 1274、读入约 242 MiB；
tier 1 对照增量 61、读入约 6.9 MiB，可用内存快照约 92 MiB。
更早 64/140 配置卡顿时，15 秒缺页 2614、读入约 468 MiB。
这支持内存回收/缺页是本次持续卡顿的重要因素，不证明已经消除所有卡点。

证据分别为 `runtime-sample-1789921719973476800.json`、
`runtime-sample-1789922385187030500.json`、
`stall-sample-1789920777400193200.json`。
最终版证据为 `runtime-sample-1789923991633776300.json`，
包含结束回合与敌人行动；5,359 个有效帧间隔，仅剔除 9 个截图相邻间隔。
180 秒系统缺页增量 81、读入约 10.3 MiB；不是零缺页或零长帧。
这些窗口不包含冷启动，不代表多幕、Boss、大量特效或全流程持续 25 FPS 已通过。

## 回归命令

```powershell
py -3 prototype/r3/build.py
py -3 -m unittest discover -s tools -p "test_*.py" -v
py -3 -m unittest discover -s prototype/p1 -v
py -3 tools/test_r3_contract.py
py -3 tools/test_touch_contract.py
```

Java 测试覆盖有序边沿/最终坐标/取消/过期事件、实际 agent 链。
`test_r4_combat.py` 对比 2,000 组 P1/Java 方向选敌输入。
`verify_r4_combat_device.py` 只允许操作隔离 review 目录；
连续回归包含 pile、四类取消、strike、high、defend、end-turn。
它要求预先准备适合测试的原生战斗，不伪造伤害或补充能量。
`sample_r4_runtime.py --seconds 90 --audio` 保存帧间隔和系统缺页原始证据。
