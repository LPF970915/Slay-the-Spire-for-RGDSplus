# 双屏界面分配与跨屏瞄准预研

日期：2026-09-20。修订：P0 已批准，R1 几何机制冻结，进入 R2 设备验证；尚未接入真实游戏。

最新审核入口：[P0 双屏目标设计与缺漏检查](P0_DUAL_SCREEN_DESIGN.zh-CN.md)。
顶部工具/状态栏保留上屏；下屏使用原生底层背景，战斗装饰前景下移且不在上屏重复。
用户已明确确认 P0 通过，允许在卡二单独实施 P1（旧称 R1）。
原型与实机证据见 [P1 几何原型](P1_GEOMETRY_PROTOTYPE.zh-CN.md)。

## 1. 本轮决定

用户已手动确认单屏游戏稳定性，并明确允许开始双屏显示与交互研究。
记录为“双屏预研启动确认”，不继续把已获授权的研究卡在旧计划的单屏门禁前。
既有验收台账中未执行的量化、全内容和触控用例仍保留，不自动改成全部通过。
本轮只读检查本地工程与正版 JAR，编写设计；不操作设备，不改变正式存档或运行包。

主方案确定为：

- 上屏以观看为主：战斗角色、敌人、背景、动画、过场及选中目标反馈；
  原生顶部工具与状态栏完整保留在上屏顶端，检视/激活主要依靠手柄。
- 下屏以触摸操作为主：手牌、能量、回合、牌堆、场景按钮、选项与确认/取消；
  不再重复设置地图/牌组/设置/药水的常驻顶栏。
- 上屏不可触摸，但上屏对象不能因此失去查看说明和选中目标的途径。
- 战斗首先保留原有“左右选牌→A 进入目标选择→左右选敌→A 确认，B 取消”。
- 重点研究“下屏拖牌的方向对应上屏敌人，上屏高亮，并用跨屏虚线箭头联动”。
- 旧方案 B（下屏完整战斗）降为兼容/比较备选，不与主方案同时展开全界面实现。
- 下屏复用当前页面最底层原生背景。战斗可组合底层背景与原生装饰前景，
  上屏停画已迁移的前景；角色脚下地面、阴影和战斗指示不因“前景”名称被误删。

“观看/操作”按用途划分，不按一条水平线裁切 PC 画面。
两个显示区域各自以 1024×768 设计；规则、随机数、动作队列和存档始终只有一份。

## 3. 统一分配规则

1. **所有必要操作都有明确输入路径。** 场景按钮以“下屏触摸+手柄”为主，
   上屏顶栏及其原生检视/药水菜单是明确的“手柄操作”例外；不承诺纯触摸完成全部流程。
2. **检视能力不因上屏不可触摸而丢失。** 顶栏、遗物、敌人/玩家状态、球、姿态优先沿用原生手柄检视；
   未覆盖项需验证并补充按键路径，而非默认复制一排下屏图标。必要时增加不遮挡内容的上下文按键提示。
3. **选择信息不能和选项脱节。** 下屏保留必要的价格、代价、数量、目标名称及危险提示；不能把代价只放上屏。
4. **每个操作只提交一次。** 上屏预览不是另一套按钮；下屏代理只指向同一个原生动作。
5. **保留原生禁用条件和时序。** 不因按钮搬迁而让敌人回合、过场、结算期间可以额外出牌或跳过。
6. **操作区稳定。** 返回/确认、结束回合、能量、牌堆位置尽量固定，不随标题长短和手牌数跳动。
7. **模态层独占输入。** 确认框、选牌、教程优先于房间按钮，遮罩同步覆盖两屏；显示遮罩不擅自暂停或继续原规则。
8. **未知界面安全降级。** 未适配场景完整保留在下屏 1024×768，上屏只做背景/状态展示；不能按“像按钮”猜测分拆。
9. **背景共享不复制玩法。** 原生底层背景可用于两屏，动画状态只更新一次；
   装饰前景只属于下屏，不复制人物、敌人、商品、文字、顶栏或 hitbox。
10. **顶栏位置不等于页面位置。** 上屏的地图/牌组/设置图标打开下屏对应页面，
    返回时恢复进入前焦点。上屏药水局部菜单及目标选择使用原生手柄路径，不要求从下屏拖出不存在的药水槽。

## 5. 战斗布局建议

上屏保留完整战斗坐标系的主要人物、全部敌人、意图和特效，不按最终帧像素裁切。
原生顶部工具/状态栏保留上屏顶端，遵循原有可见性，不在菜单/过场里强造不存在的顶栏。
下屏以当前原生最底层背景打底，再放装饰前景；手牌整体上移，能量与牌堆、结束回合各有安全区。
已迁移的装饰前景只在下屏画，上屏停画；原生背景可以在两屏显示，但状态不能更新两次。
不能把整个 `renderCombatRoomBg` 当成一张纯背景，也不能把人物地面/阴影/提示误归为装饰前景。

下屏初始布局范围（设计起点，坐标原点在左上；不是已定稿的像素参数）：

| 区域 | 建议范围 | 用途 |
| --- | --- | --- |
| 联动瞄准/详情区 | y=0～400 | 原生背景、目标提示、拖拽方向、非瞄准时的详情；不设常驻工具栏 |
| 完整手牌区 | y=400～704 | 扇形手牌、选中抬起与适度放大 |
| 底部安全区 | y=704～768 | 边缘留白及固定牌堆/回合控件的布局余量 |

左右侧也预留能量、牌堆和结束回合空间；该表不是四条全宽互不重叠的最终组件框。
必须用真实卡牌外轮廓计算边界，不只检查 `hb`；5 张、10 张和选择抬起各测。
允许满手牌相互遮叠，但每张牌的费用/选择入口应可辨；选中后必须完整显示。
详情可临时占用瞄准区；开始拖牌时收起，不能让详情面板挡住目标反馈。

拖牌期间其他按钮不抢手势。尤其松手位置恰好落在“结束回合”上，也只能取消拖牌，
不能同时结束回合。松手后必须重新按下才产生下一次按钮操作。

### 5.1 背景与前景规则

“最后一层背景”在本文明确指视觉最底层/最远景，不是最后执行的 draw call 或最终整帧截图。
每个页面的背景归属见 P0 审核文档的 B01～B08；包含无独立背景的弹窗/选牌页处理。
层次约定：

```text
上屏：原生背景/必要地面 -> 人物与战场效果 -> 顶栏/原生检视 -> 模态/过渡
下屏：原生底层背景 -> 迁移的装饰前景 -> 手牌/场景操作/卡牌动画 -> 联动箭头/浮层 -> 模态/过渡
```

这是归属约定，不强行重排原生战场特效和顶栏效果的内部顺序。
前景不得盖住卡牌、按钮或箭头；没有独立前景的页面不人为添加战斗装饰。
模态页沿用当前场景背景并叠加原生遮罩；切换房间/章节需使缓存失效，不能残留上一幕。
若无法安全独立取出背景，先记录场景为待适配或完整下屏降级，不擅自用别页背景或外部图片替代。

## 6. 三套坐标与联动选敌

### 6.1 区分游戏、物理排列与输出排列

```text
游戏原生坐标：1024×768，保留 Settings 的 4:3 逻辑
每屏显示坐标：上屏 1024×768；下屏 1024×768
联动虚拟坐标：两屏纵向排列，中间留出可配置的铰链间距 g
输出坐标：按当前 Wayland/SDL 实测布局组合，可能是横向排列
```

箭头计算使用纵向联动画布，不能沿 Weston 的左右排列画一条横跨窗口的箭头。
采用左上原点的设计坐标时：

```text
上屏点 (x,y) -> V=(x,y)
下屏点 (x,y) -> V=(x,768+g+y)
```

`g` 先作为可调视觉参数；如果实际屏宽、位置不同，再用各屏独立仿射变换校准。
不可从 DRM 报告的毫米尺寸直接推定机壳上下屏几何。
输出贴图、GL viewport/scissor 和原游戏 y 向上的坐标分别转换，不能混用。

### 6.2 推荐：方向射线 + 小范围吸附 + 稳定目标

1. 触下记录卡牌实例与指针起点 `P0`；起点固定，不随卡牌抬升/放大漂移。
2. 超过拖动阈值后抓起卡牌。只有明确向上拖、离开原手牌安全带才进入瞄准态。
3. 用指针 `P-P0` 的方向构建向上射线；候选为本次战斗当前仍可选的敌人。
4. 将敌人的原生 hitbox 投影到上屏，再映射到联动画布，比较射线与目标角区间。
5. 先考虑射线实际穿过的目标范围，再作有限角度吸附；不要无条件选“最近的敌人”。
6. 命中不唯一时保留明确的歧义状态，或使用已选目标的滞回；不得按数组先后悄悄选定。
7. 手势方向稳定时保持已选对象；新目标明显更接近方向才切换，避免轻微抖动来回跳敌。
8. 每帧目标结果同时驱动上屏高亮、下屏目标名与箭头端点。松手只允许提交最近已显示且仍有效的目标。

拖动阈值、向上距离、吸附角与滞回范围均是后续可调实验参数，不在预研中冒充最佳手感。
初始数值可从约 12～20px 拖动阈值、60～90px 向上位移试起，实机以误触率/舒适性定值。
手指始终可以停留在下屏中部，不要求触碰边缘；顶部边缘丢失触点不能视作可靠松手提交。

纯角度方案的限制：多个敌人从 `P0` 看过去几乎重叠时，单靠方向不能可靠区分。
这包括同列/前后遮挡、两侧包围及满场小目标；不是多加一个吸附系数就能解决。
保留两种精确路径：

- 必备：原生左右按键切换目标。
- 待比较：下屏瞄准区中的小型“目标带/目标位置图”，使用同一目标身份，可直接指向选择。
  它是增强精度的交互视图，不复制敌人或规则；不要在同一手势中无提示切换选敌算法。

先比较方向方案与下屏绝对位置映射的对照结果，再决定目标带是否常显。

### 6.3 松手不是跳过原生校验

提交前检查：仍是玩家可操作阶段、卡牌还在本手牌、没有新模态层、目标仍有效、
本次手势未消费，且原生提交路径允许使用。合法性/能量/特殊限制仍由原游戏判定。
不能从适配层直接扣能量、调用牌的效果或自行塞入规则结果。

若目标在松手前死亡/离场、卡牌被移除、选中结果尚未显示，取消或保持未提交状态；
不自动换到另一个敌人。预览与提交都以实例身份为准，不使用 `cardID` 或敌人列表下标充当唯一身份。
同名同牌、召唤替换、列表重排都必须能区分。

| 原生目标类型 | 交互设计 |
| --- | --- |
| `ENEMY`、`SELF_AND_ENEMY` | 单个合法目标高亮，箭头指向它 |
| `ALL_ENEMY` | 高亮全部受影响敌人，显示范围语义，不画误导性的单目标箭头 |
| `SELF` | 玩家获得受影响反馈，下屏合法释放区即可操作 |
| `NONE`、`ALL` | 按实际牌语义走无指定敌人的释放路径，不能假装都需要选敌 |
| 随机目标效果 | 显示随机/原生说明，不预先选择或泄露随机结果 |
| 需后续选牌的效果 | 本次提交结束后切到 U14/U15/U16，旧箭头立即清除 |
| 药水 | 顶栏仍在上屏，先保留原生手柄使用/选敌及上屏箭头；不套用下屏卡牌拖动起点 |

费用不足、不可打出、目标不合法时不提交；保留原生原因反馈，回手后仍可继续选牌。
拖回手牌、向下拖回取消带、B、失焦或触摸异常均能撤销。

## 7. 跨屏虚线箭头

**可以设计为一条视觉连续的路径，但两块屏幕之间的实体铰链不能发光显示。**
效果是下屏的线抵达上沿，上屏的线从下沿接续，最终指向敌人；中间留白不可避免。

推荐在同一个纵向联动画布生成一条曲线，然后按两屏可见矩形裁剪：

```text
上屏：                      [高亮敌人]
                                 ↑
                              ·  ·
上屏下沿 --------------------·--------
                  铰链间隙（不绘制）
下屏上沿 -----------------·-----------
                        ·
                      ·
                   [拖动卡牌]
下屏：             手牌 / 操作区
```

- 始端为卡牌顶部/拖动控制点，末端为目标轮廓上的可辨识锚点，不遮盖血量与意图。
- 曲线起始切线尽量跟随拖动方向；目标吸附后末端轻微弯向敌人，不能突然拐向远处目标。
- 同一条路径、同一时间相位和同一弧长虚线节奏；不是两屏各画一根各自跳动的箭头。
- 使用虚拟间距 `g` 时，两屏边缘交点可有合理水平位移；不能为强求相同 x 而折断切线。
- 无目标时显示中性方向提示；有合法目标时才显示明确箭头尖端与目标轮廓。
- 有候选但不能出牌时同时用样式和文字区分，不能只靠红绿颜色。
- 松手成功、取消、打开弹窗或目标失效时两段一起清除。
- 震屏/敌人动作时使用同一帧的投影；可以平滑视觉端点，但不能因此滞后切换实际目标身份。
- 只在上屏画攻击/伤害特效；跨屏箭头属于下屏发起的操作提示，不复制伤害动画到下屏。

第一原型先做“高亮正确”，第二步连直线/折线，最后再加平滑曲线、虚线与动态流动。
箭头美观不能优先于目标正确性。

## 8. 手柄兜底与触摸仲裁

原生手柄导航继续工作，不改方向键的基础语义：

```text
选牌态：左右选择手牌 -> A
选敌态：左右选择敌人 -> A 确认；B 取消
```

拟定统一操作状态：

```text
Idle -> PressedCard -> Dragging -> Aiming -> CommitOnce -> Idle
                                  |          |
任意活动态 -> Cancel/Release -----------------> Idle
```

另保留 `ControllerCardSelect` 和 `ControllerTargetSelect`；两路共享 `Selection`，
但每次操作只有一个输入 owner 和一个递增 `gestureId`。

- 增加 `TopPanelFocus`：只有原生允许进入时才可进入；先取消当前卡牌拖动并消费旧触点，
  防止上屏确认药水时下屏同时出牌。退出后重新按下才恢复下屏触摸。
- 顶栏打开下屏全页后，焦点转给全页；B 返回已记录的上一层，而不是同时关闭顶栏和取消手牌。
- 原生不允许切换顶栏的阶段不强行切换；长按退出守护仍始终可用。
- 触摸拖牌期间普通方向键不同时推动另一套鼠标/目标状态。
- 第一版允许 B 随时取消，再用纯手柄重选，保证可靠兜底。
- 混合增强：有效左右按键可显式接管当前选敌，保留卡牌选择；
  接管时结束触摸 owner，忽略该旧触点后续移动/松手，需 A 才能出牌。
- A 接管确认和触摸松手同帧到达时只能有一个提交；释放事件仍需清理，不能丢弃成悬空拖拽。
- 完成/取消后，要等所有原按键/触点释放，再接受新操作，避免持续按住重复出牌。
- 第二指不能变成第二个 owner；`SYN_DROPPED`、设备丢失、场景/模态变更、队列溢出都取消。
- 迟到的 UP/CANCEL 应清理它所属的旧手势，但不能取消后来新建的手势。

Balatro 的“释放不能被 generation 校验吞掉”值得借鉴；不能照搬为“所有坐标事件免校验”。
过期坐标在商店/奖励页可能命中新商品或新选项，需同时绑定场景代次和手势身份。

## 9. 技术接入与主要风险

### 9.1 分层，而不是双实例或双次完整 render

拟新增独立的布局/输入组件，不把所有逻辑塞入当前 `InputAgent`：

| 拟议组件 | 职责 |
| --- | --- |
| `SceneLayoutRegistry` | 声明当前场景的对象归属、显示变换、输入入口与模态优先级 |
| `RenderRouter` | 在原调用位置切换视口/矩阵/裁剪，确保交互对象/前景归属唯一；允许显式共享底层背景展示，不重复更新 |
| `PointerRouter` | 输入源去重、owner、屏幕局部坐标、逆向命中与可靠释放 |
| `TargetSelection` | 方向候选、滞回、原生手柄结果同步，保存唯一目标身份 |
| `CrossScreenArrow` | 消费同一份选择快照，只画跨屏路径，不改变规则 |
| `InteractionGuard` | 场景/手势代次、提交一次、取消与降级 |

名称仅为设计，不表示已创建类或确定最终抽象数量。
配置开关需把双屏作为独立实验模式；稳定单屏启动项、存档格式与退出守护保留。

### 9.2 已发现的关键接入点

| 区域 | 已检查的入口 | 研究任务 |
| --- | --- | --- |
| 总循环 | `CardCrawlGame.render/update` | 保持一次 update；严禁为上下屏重复调用整个 render |
| 战场/前景 | `AbstractDungeon.render`、`AbstractScene.renderCombatRoomBg/Fg` | 在原调用顺序路由；确认每幕 foreground 不混含其他必须上屏对象 |
| 人物/手牌 | `AbstractPlayer.render`、`renderPlayerBattleUi`、`renderHand` | 拆开战场实体、手牌、检视和瞄准；不凭一个方法名推定内部全属同屏 |
| 瞄准/出牌 | `updateInput`、`updateSingleTargetInput`、`updateControllerInput`、`playCard`、`releaseCard` | 找到原生合法性与目标确认的可靠插入点，不在循环开头随意覆盖字段 |
| 牌规则 | `AbstractCard.canUse` 与原生动作队列 | 不重写规则；验证目标筛选预览不会调用有副作用的校验多次 |
| 能量/牌堆/回合 | `OverlayMenu`、`EnergyPanel`、`DrawPilePanel`、`DiscardPilePanel`、`ExhaustPanel` | 原显示、输入和禁用状态一起迁移 |
| 顶栏/药水 | `TopPanel`、`PotionPopUp.updateTargetMode/renderTargetingUi` | 顶栏保留上屏；核验手柄、局部菜单与下屏全页的焦点切换，药水箭头不误从下屏发出 |
| 详情/浮层 | `TipHelper`、`SingleCardViewPopup`、`SingleRelicViewPopup` | Tooltip 全局队列与一次绘制限制；模态遮罩不跨屏穿透 |
| 底层指针 | `InputHelper.updateFirst/updateLast`、`Hitbox.update`、`LwjglInput` | 不能只改 `InputProcessor`，还要检查轮询、游标自动移动和 controller-mode 切换 |

特别风险：

- 多组对象拥有不同显示变换，却共享一个 `InputHelper.mX/mY`。必须限定当前输入归属，
  或在具体 hitbox/调用域做逆变换；全局缩放一次鼠标坐标不能同时解决上下屏命中。
- 控制器会通过原生游标定位选牌/选敌；游戏游标、物理下屏触点、适配层显示箭头要分离。
- 卡牌 `current_x/target_x/angle/drawScale` 兼有动画与布局语义，先研究显示变换，
  不为了放大卡牌永久改写原规则对象中的插值目标。
- `renderTargetingUi()` 含状态修改；将状态演进限定一次，额外跨屏路径只读快照，
  或仅替换经审计的绘图片段，不把整个瞄准函数绘制两遍。
- 不能只绘制 `renderHand` 而漏掉抽牌/弃牌/消耗/获得卡牌的 VFX；
  特效需按语义分配，卡牌飞行归下屏，命中战场归上屏，跨域效果单独规定。
- 双屏试验不得重新引入已经修复的 ASTC 输入格式、小纹理回退、短按和 R2 映射问题。

### 9.3 显示与资源方案

优先验证同一窗口两块输出区域的可行性，不先承诺 2048×768 窗口必然跨屏成功。
当前辅助 XWayland 与真实系统 Wayland 的角色不变；不能只改辅助窗口尺寸就算完成输出。
游戏逻辑尺寸保留 1024×768，输出尺寸由独立显示层管理，禁止全局把 `Settings.WIDTH` 改成 2048。

首选在同一上下文中路由绘制；是否引入每屏 FBO，取决于状态隔离和实际成本。
切换前处理 SpriteBatch/PolygonSpriteBatch 的待提交顶点，并成对保存恢复矩阵、
viewport、scissor、混合、shader、纹理和 framebuffer；异常路径也需恢复。
不能假定绑定默认 framebuffer 等于回到外层 FBO，或 GL 状态变了 batch 缓存也会跟着变。

1024×768 RGBA8 单张色彩附件约 3 MiB，两张约 6 MiB；
不包含深度/模板、多缓冲、驱动开销和原游戏纹理。
禁止通过每帧 CPU 截图/像素回读合成双屏；已有诊断截图仅供测试。
背景降分辨率只能作为后续性能实验，文字、卡牌和图标不得跟着模糊。

## 10. 分阶段研究与验收

P0 目标设计（即原 R0）已获用户确认；P1 / R1 已按几何范围收尾，
见 [R1 冻结与移交](R1_CLOSEOUT.zh-CN.md)。
[R2 探针](R2_TOUCH_PROBE.zh-CN.md)实体项待验；用户随后授权离机继续，
[R3 真实 UI](R3_NATIVE_UI.zh-CN.md)已独立接入菜单、战斗和牌堆。
这里的 P0 是双屏设计阶段，不是旧“单屏 P0”或缺陷严重度 P0。

| 阶段 | 产出 | 继续条件 |
| --- | --- | --- |
| P0 / R0 界面/目标设计 | 本文、P0 审核表、覆盖索引、风险列表 | 用户已于 2026-09-20 明确批准 |
| R1 纯几何交互原型 | 无游戏资源的双屏目标/拖拽/箭头实验 | 左/中/右起手，1/2/5 敌人、重叠/左右包围、取消和按键接管均有轨迹证据 |
| R2 设备输出与下屏命中探针 | 输出身份、坐标变换、单指输入与退出 | 角点/网格误差目标 ≤8px；无重复输入；不写固件持久设置 |
| R3 隔离战斗原型 | 上战斗、下手牌/控件，先按键后触摸 | 200 次出牌/取消零错牌错敌/重复扣费；箭头目标与提交目标一致 |
| R4 全界面路由 | U01～U33 逐页适配/明确降级 | 场景交互在下屏，顶栏及检视有手柄路径，无信息丢失和输入死路 |
| R5 双屏体验与交付 | 物理视频、帧时间、长稳、回退和用户签认 | 继承冻结单屏性能基线；不能以研究授权代替发布验收 |

跨屏联动专项验收：

- 同一帧上屏高亮、下屏目标提示、箭头端点、原生选中目标身份一致。
- 2 轮各 20 次用户指定目标任务；首次目标命中率目标 ≥95%，记录取消率和耗时。
- 同角度/遮挡目标无法可靠区分时，明确用手柄或目标带，不把错选归为“手感问题”。
- 覆盖四角色、零费/X 费、群体/随机/自身目标、非法出牌、药水、目标死亡、生成/移除牌。
- 两屏边缘路径裁剪无长条溢出；截图只能证实各段存在，实体视频才验证视觉接续。
- 同帧触摸松手+A、B+松手、失焦+松手、旧手势释放晚于新手势都只能产生安全结果。
- 对同版本隔离存档/同操作序列比较费用、目标、HP、格挡、动作数与随机结果；
  不能只看画面“像是在玩”。
- 原生 24 FPS 基线不因双屏自动降低；同时记录 update 次数、逐帧耗时、系统内存和音频。
- 任何未知场景保留下屏完整交互；不存在“对象被上屏隐藏、下屏又没有画”的空洞。

## 11. 当前建议

优先顺序是：**全界面归属声明 → 按键双屏战斗 → 方向拖拽选敌 → 跨屏箭头 → 全界面交互回归**。
P0 已获确认，R1 几何原型已实现并冻结；依用户最新授权，R3 真实战斗 UI
和按键路径已隔离推进，R2 剩余实触验证不标记通过。
下一步结合用户远程审图接入真实触摸命中和方向拖牌。
抽象素材不继续承担最终美术和手感定稿。

主交互采用方向拖拽并给出有限目标吸附；不要求手指跨过铰链。
原生按键选敌是永久可用路径，不是只在调试时才启用的补救。
目标带是否常显、吸附强度、手牌放大比例和铰链虚拟间距由原型试用决定，
不在本次预研中写死。
